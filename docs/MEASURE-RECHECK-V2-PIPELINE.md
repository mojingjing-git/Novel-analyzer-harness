# 复检 V2 走生产管路的实测（2026-10-31）

## 结论

| 项 | 数值 |
| --- | --- |
| 分析规模 | 16 章 / 128,623 字（三侠五义前 16 章） |
| 并发 | 8（`config.analysis.concurrency`），`block_size=1` |
| 分析耗时 | **1,051 秒**（16 块，含预热） |
| 分析结果 | `total_analyzed=16`，`errors=[]` |
| 账本候选 | 60 条，全部带锚点 |
| 复检 | **0/60 核对**——12 次调用全部因 `prompt is too long: 100001 tokens > 100000 maximum` 失败 |

## 这轮暴露的设计错误（重要）

`recheck_v2` 把**整本书正文**拼进 prompt 当证据。16 章就已经 100k token，
整本 64 章约 400k token——**任何模型都装不下**。这不是"调小 batch"能绕过的，
是证据选取策略错了。

正确做法（下一轮改）：prompt 里只放**该候选锚点所在章的正文**，并在必要时截断成
"锚点前后窗口 + 截断标记"；定位（程序侧）仍用全文，所以校验精度不受影响。

## 走管路的注意点（踩过）

- `AnalysisPipeline` 的落盘位置由 `config.working_directory` 决定，**不是** `directory.parent`。
  不设就落到 repo 根 `output/`（本次已踩，产物已搬回）。
- 并发 8 下 16 章 1,051 秒 ≈ 每章 66 秒墙钟；整本 64 章按此推算约 1 小时（比串行 4 小时快 4 倍）。
