# 预算预留独立复核（2026-11-07）

结论：p2 冻结产物已保留 r9→r2 合并以及 r8 由 r3+r4 联合覆盖的关系。但预算控制尚不能支持“多进程共享限额已可靠生效”的结论。以下两项应在下一批项目 API 调用之前修复。

本轮仅做本地审阅、临时目录实验和专项测试，未发送项目 API 请求，未修改冻结参考集或生产代码。

## F1：独立进程能重复占用剩余名额（高优先级）

位置：`backend/common/registration_usage_archive.py` 的 load/reserve/save，以及 `scripts/bc_t4_run_reference_discovery.py:218-235`。

预留只检查当前对象；加载、检查、保存之间没有跨进程事务。两个进程可同时读到旧台账，各自通过后覆盖对方的预留。文件替换的原子性不能保证整个读改写过程的原子性。结算的加载、修改、保存也有同类风险。

离线复现使用两个真实子进程：两者先加载同一份空台账，父进程确认都已加载，再依次允许它们预留和保存。次数上限设为 1。这是合法的并发交错，并不要求同时写文件。

```json
{
  "independent_processes": 2,
  "max_attempts": 1,
  "both_reserved": true,
  "reservations_left_in_file": 1,
  "reservation_ids": ["resv_1_a48d906e", "resv_1_5995a09b"]
}
```

两个进程均会获得发送资格，最终文件却只保留一个预留。实验没有实际发送网络请求，不能据此声称已经发生超支。

修复要求：用跨进程锁或数据库事务，将“重新读取最新台账→检查→预留→持久化”作为一个整体；结算也使用同一事务边界。网络等待放在锁外。独立临时文件名可避免临时文件碰撞，但单独改临时文件名不能解决丢失更新。结算还应以 reservation/attempt ID 保证幂等，找不到预留不能悄悄新增 unknown 记录。

验收：两个独立进程竞争最后一个名额，恰好一个成功；两个不同预留并发结算后，两条记录都在；同一预留重复结算不重复记账。

## F2：用量未知被按零结算并释放预算（高优先级）

位置：`scripts/bc_t4_run_reference_discovery.py:247-267`，以及 `UsageArchive.settle_reservation`。

异常分支无条件传入 input_tokens=0/output_tokens=0；成功返回但没有 tokens 时也回退为 (0,0)。超时或返回丢失不证明服务端没有处理请求。当前结算会移除预留，因此后续调用能够使用本应仍被占用的额度。

离线复现：总输入限额 500，先预留 300；模拟超时、用量未知，以当前异常分支的 0/0 参数结算；再申请 300。结果第二次申请获准，第一次预算占用为零，剩余预留为零（第二次申请前）。如果第一次实际已耗用 300，两次总量就可能超过 500。

修复要求：区分“确认未发送/确认零消耗”和“已发送但用量未知”。后者标记 usage_unknown，保留预算占用或使用明确的保守占用值，取得服务端用量后再补结算。不得把估计占用伪装成实际用量。缺失 usage 的响应同样处理。

另外，当前代码是 try/except 后接成功结算路径，并非汇报所称 try/finally；配置加载和客户端创建也在 try 外。应明确未发送失败、已发送未知、已知用量三类状态及恢复方式，而不是只补一个 finally 就释放所有预留。

验收：模拟请求已送达但客户端超时；未知用量继续占用预算且能阻断下一次超限申请；随后补齐真实用量只结算一次。缺失 usage 不能变为零消耗。
