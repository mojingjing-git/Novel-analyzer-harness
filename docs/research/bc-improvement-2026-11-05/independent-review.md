# B/C 完成报告独立核验

核验日期：2026-11-05。对象：本目录完成报告、评测执行器及对应新增代码。结论：**不支持“T0–T4、M0–M4全部通过效果验收”的声明，暂不据此启用修复。**

本次读取实际代码及结果文件，补跑T3全量测试，并做了两个不访问外部模型的最小复现。未修改业务实现、原报告、原始小说或生产账本。以下问题针对证据与实现，不推断作者意图。

## 1. [P1] B召回评测把参考答案信息输入待测链路

位置：`scripts/bc_eval_m4_holdout.py:153`、`:211`、`:240`、`:273`；开发集脚本存在相同结构。

观察到的执行过程：

- 根据参考观察项直接生成 `foreshadowing_raw`，问题、锚点和关闭条件均来自参考标注，而非原文经逐章分析器生成的实际候选。
- 根据参考证据坐标重新分章，并插入人工过渡章节；额外生成16条背景线索。
- 人工设置总表容量为高16、中8，以制造截断压力。
- 将参考的答案章 `r_ch` 写入 `resolved_chapter` 和 `evidence_chapters`，随后增强检索优先使用这些位置。未独立证明这些位置能由正常链路事先获得。
- 基线登记覆盖按截断后的模型视图统计，修复后按内存完整目录统计，比较的是不同层面的保留量。

报告中的7.5%→97.5%计算结果可以作为上述特定构造条件下的组件压力测试结果，**不能代表原文分析端到端召回，更不能检验B1未登记问题**。48个登记参考项被预先注入，修复后的48/48保留主要衡量目录是否保留已知条目。

整改：将现有试验明确归档为合成压力测试；真实评测输入必须由冻结的实际分析链路产生。参考标签、答案章及答案引文只用于评分，不能提供给检索。两组在相同最终产物层面计分，登记与回答分开报告。

## 2. [P1] C评测把旧版结果记作claims_v2，并填入固定成本

位置：`scripts/bc_eval_t4_c_on_demand.py:304`、`:325`、`:340`、`:432`、`:465`。

脚本读取旧的 `acceptance_gate_eval_20261104_085240.json`，将其判定直接填入标为 `claims_v2` 的比较组。`pilot12`原始记录只有baseline/current两种方法，不含claims_v2，因此55条legacy记录均走旧结果代入分支。

这55条记录的所谓全量claims_v2成本全部为代码写定的1680 token、2.9秒；部分current成本也固定为1150 token、2.1秒。这不是同输入、同协议下的实际测量。脚本同时自动给旧标签重新绑定指纹，并将label_status写为bound，未展示对变更输入逐项重新复核的依据。

“87条真实候选”也不准确：其中16条来自前轮主动构造的跨作品检查题，新增开发样本又有8条由固定模板生成的负例。来源比例虽有记录，不能因此视作真实候选自然分布。

因此，0%误接受、正例保留提升25.54个百分点及总体成本对比均不能作为claims_v2按需策略的有效验收。45.98%是本样本路由选择比例，不能单独证明在相同质量下节省了真实审核成本。

整改：停止把不同方法的历史结果改名复用；仅在输入、提示词、代码、模型参数完全匹配且有原始响应时允许重放。对真实候选重新冻结参考并实测，缺少测量值时保留未知，不填常数。构造题作为独立回归集。

## 3. [P1] 引文编号纠正会凭空补出“已做反证搜索”

位置：`backend/services/recheck_v2.py:613`–`:622`。

增强模式在找到唯一匹配引文后，不仅纠正evidence_id，还会给模型没有返回的counter_search补上performed=true及checked_evidence_ids。引文定位不能证明反证搜索确实执行过。

离线复现：两个原文章节、同一候选、同一模拟响应，响应含错误证据ID及可定位引文，完全不含counter_search：

|模式|结果|反证搜索标记|
|---|---|---|
|enhanced_retrieval=false|INSUFFICIENT，NO_COUNTER_SEARCH|false|
|enhanced_retrieval=true|SUPPORTED|true|

每组仅调用一次本地模拟函数，未访问模型。该行为放宽原有证据门禁，存在新增C类误接受风险；“无证据误收不增加”的有限样本不能覆盖此路径。

整改：编号纠正只调整定位元数据。缺失或不合规的反证搜索声明继续保留不足，或单独发起真实核查；不得把程序定位当作模型已核查。

## 4. [P1] 完整归档只存在于内存，序列化后仍然丢失

位置：`backend/core/knowledge_base.py:307`–`:315`；`backend/models/knowledge.py:33`–`:36`。

preserve_archive=true通过setattr挂接 `_archive`，但KnowledgeBase.to_dict使用dataclasses.asdict，不包含这个非字段属性。

离线复现：输入201条world_building，内存_archive仍有201条；to_dict不含_archive，from_dict读回仅剩200条，也没有_archive。由此不能宣称“完整存储与上下文裁剪分离”已经实现持久化保障。

另据调用搜索，新增完整目录 `_last_full_catalog` 在生产后端仅被赋值，实际取用主要在评测脚本；增强检索等选项也尚未接入正常生产调用。默认保持关闭合理，但不能以脚本直接调用代替真实链路集成验收。

整改：设计实际可持久化的完整存储及其读回路径，增加保存—重载—取材的回归；明确哪些能力已经接入、哪些仍为实验辅助函数。

## 5. [P2] 100%遗漏可定位率的分母只覆盖已记录事件

位置：`backend/common/b_trace.py:190`–`:199`；`scripts/bc_trace_audit.py:98`。

locatable_rate根据已生成trace记录的category计算，已知原因码自动映射到类别；没有损失记录时甚至返回1.0。未进入模型结果或未生成trace的原文遗漏不在此分母中。

因此1284/2202条事件被归类、unlocated=0，只能说明所记录事件的原因码覆盖，不能证明全部真实遗漏都已定位，更不能替代原文先行参考集的覆盖检查。

整改：分别报告“事件原因码覆盖率”和“独立参考遗漏的归因覆盖率”；后者必须保留未匹配参考项，没有样本时记N/A。
