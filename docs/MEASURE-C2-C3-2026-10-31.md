# C 批实测（C1 / C2 / C3）——2026-10-31

三份原始数据：`docs/MEASURE-C1-2026-10-31.json`、`docs/MEASURE-C2-2026-10-31.json`、
`docs/MEASURE-C3-2026-10-31.json`。标注集：`docs/annotations-C2-2026-10-31.json`（30 条）。

**样本量都很小，下面所有比例都不给置信区间。** 它们能支撑"有没有系统性问题"，不能支撑"准确率是多少"。

## 一、C1：真实模型能不能把整本跑通

| 项 | 值 |
| --- | --- |
| 语料 | 合成 23 章（第 17 章缺失）→ 实建 22 章 |
| 块 | 4 章/块 → 6 块 |
| 调用 | **6 次**（每块 1 次，attempts=6，无重试） |
| token | prompt **6,316** / completion **43,561** / 合计 **49,877** |
| 未知用量 | 0（全部 `usage_status=KNOWN`） |
| 耗时 | 244 s |
| 结果 | `stop_reason=completed`，`commit_cursor=6`，`prefix_complete=True`，`gaps=()` |
| 第二次运行 | **0 次调用**（缓存命中），覆盖结论不变 |

每块约 8,300 token，每章约 2,270 token（含 4 章正文 + 窗口 + 输出）。**输出占 87%**（43.5k/49.9k），
说明成本主要由"模型写回的分析 JSON"驱动，不是由正文驱动。

## 二、C2：事实核查环节的召回与误报

标注：30 条（SUPPORTED 20 / NOT_STATED 5 / CONTRADICTED 5），覆盖语料里**全部 10 个有实质正文的章**，
引文 30/30 都是正文逐字子串（我独立复验）。

| 指标 | 值 |
| --- | --- |
| 召回（支持→SUPPORTED） | **0.45**（9/20） |
| 误报（非支持→SUPPORTED） | **0.00**（0/10） |
| 判 SUPPORTED 时引文通过逐字校验 | **1.00**（9/9） |
| 精确匹配率 | 0.633（19/30） |

混淆矩阵全部失分集中在一处：

```
SUPPORTED → SUPPORTED      9
SUPPORTED → INVALID       11   ← 全部是 QUOTE_OUT_OF_RANGE
NOT_STATED → INSUFFICIENT  5
CONTRADICTED → CONTRADICTED 5
```

也就是说：**判定没出错，是偏移出错了。** 模型判"这条被支持"的 20 次里 11 次给出对不上的
`supporting_span`，被门禁判 `INVALID`。而 `INVALID` 在契约里是**可重试**的——生产环境会
把这 55% 再花一遍钱。

"误报 0"这条要读准：它说明门禁**失败关闭**（拿不到可定位证据就不认），不说明模型不会误判。

## 三、C3：重复采样与证据顺序

3 个候选 × 2 种顺序（故事序/逆序）× 3 次采样 = 18 次调用，67,451 token，354 s。

| 判定 | 次数 |
| --- | --- |
| SUPPORTED | 12 |
| INVALID（QUOTE_OUT_OF_RANGE） | 5 |
| INSUFFICIENT | 1 |

- **"不稳定组 5/6"是误导性的**：拆开看，不稳定几乎全部是 `SUPPORTED ↔ INVALID`。把 `INVALID`
  （解析失败，不是判定）剔掉之后，13 次有效判定里 12 次 SUPPORTED、1 次 INSUFFICIENT —— 判定本身稳定。
- **顺序确实有影响**：逆序 6 次里 4 次 `INVALID`，故事序 6 次里 1 次。模型仍能找到正确内容，
  但偏移算得更差。
- 三个候选里 `cd_0003`（同章先埋后收）在故事序下 3/3 SUPPORTED —— 最容易的一类。

## 四、三条契约级发现（不是模型问题）

1. **Prompt 的 JSON 键名必须与解析器逐字一致，且没有机制保证。**
   我第一版写 `supporting_evidence_id`（解析器读 `evidence_id`）→ 18 次调用全 `NO_EVIDENCE_ID`；
   第二版改对 `evidence_id` 却把 span/quote 写成 `span`/`quote`（解析器读 `supporting_span`/
   `supporting_quote`）→ 15/18 `NO_SUPPORTING_QUOTE`。两轮共烧掉 36 次调用、约 109k token，
   全部是"键名对不上"，不是判定能力问题。
   **建议**：把"解析器读哪些键"生成成常量并从同一个来源产出 Prompt 片段，加一条用例锁死。

2. **`quote_within_range(quote, start, end)` 拿不到 `evidence_id`**，因此无法验证"这段引文属于
   模型点名的那一段证据"。现在的校验只能回答"这段文字在**某**段证据里对得上"。这是契约缺口，
   不是实现疏忽。

3. **偏移基准是隐含的**（相对片段？相对整条消息？），调用方各自解释就会各错一次 ——
   C2 首轮我按整条消息校验、模型按片段给偏移，召回直接掉到 0.00。

## 五、最值得改的一处

**让模型只给引文，偏移由程序算。**

现在的接口是"模型自己数偏移 + 给引文"，于是每一次失败都要重试一次完整调用。改成
"模型给逐字引文 → 程序 `str.find` 定位 → 程序算出 span 并校验"，可以把
C2 的 11 次 `QUOTE_OUT_OF_RANGE` 与 C3 的 5 次全部变成成功，而**不增加任何调用**，
同时保留"引文必须逐字命中"这条反伪造闸门（找不到就是不认）。

代价：程序要处理"同一引文出现多次"（取首次出现 + 记录歧义），以及跨段引文（拒绝）。
建议记为 **D-19**，在下一批里做；本轮只记录证据，未改实现。
