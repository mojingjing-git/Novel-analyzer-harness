## 审查范围与最新约束

用户已明确：不考虑以前的旧产物兼容，作为新大版本直接重新开始。因此，本次不把历史 JSON 兼容、旧账本迁移、旧状态投影或迁移报告列为实施条件。

仍需保证新版本自己的补跑、断点恢复、重复总结和输入变更不会串数据。这里的“重建前后”均可以发生在新版本生成的数据中，不依赖旧版本数据。

## 必须补齐的问题

### R1 · P1 · B1 按块起始章过滤，不能保证整个块早于当前章

**依据**：`backend/core/pipeline.py:300` 按本次选择的章节重新分块；`backend/core/memory_state.py:249` 恢复时验证块大小，`:131` 按结果的起始章号筛选；`backend/models/analysis_result.py:114` 只有 `block_size`，没有实际章节集合。

**触发方式**：本版本先分析块 `[1,2,3]`，随后从第 2 章开始分析，形成 `[2,3,4]`。按 B1 的 `chapter_limit = block_start - 1`，起始章号为 1 的结果仍被纳入，实际却包含第 2、3 章。

**隔离复现**：将 `chapter_number=1, block_size=3`、含事件“第3章秘密”的结果落盘，再以相同块大小恢复；请求 `get_kb_snapshot(chapter_limit=1)`，返回事实仍包含“第3章秘密”。

**修订要求**：将实际 `source_chapter_ids` 和源内容版本/指纹纳入新结果 schema。快照只使用所有来源章均早于当前块的结果；续跑复用必须验证块组成与内容，不能只验证起始 ID 和大小。对无法证明范围安全的结果禁用复用。

**补充验收**：块大小不变但起始分析范围改变、断号章节、源文件新增/修改，以及重叠块恢复。

### R2 · P1 · C1/C3 缺少稳定伏笔身份，补跑会把状态挂到另一条线索

**依据**：`backend/utils/text_utils.py:325` 以分组顺序生成 `fs_001` 等 ID；`backend/services/final_summary.py:1524` 仅按 ID 判断账本条目是否存在；`:1321` 同样只凭 ID 应用回收结论。

**隔离复现**：先只有第 10 章的“王冠秘密”，ID 为 `fs_001`；补入第 1 章完全不同的“孤岛线索”并重建后，孤岛成为 `fs_001`，王冠变为 `fs_002`。旧状态留在原 ID 上时，就会错误关联。

新大版本第一次运行后发生一次早期补跑，就足以触发，不属于历史兼容问题。C2 的“ID 存在”校验无法识别这种错配。

**修订要求**：区分稳定实体 ID、原始线索 occurrence/source ID 和展示编号。合并/拆分显式维护来源映射；候选绑定实体与来源版本，来源变化时失效或重新校验。目录更新时同步证据及最后出现章，而不只是追加“不存在的 ID”。

**补充验收**：补入前序章节、调整筛选条件、去重分组拆分/合并后，既有结论不得转移给别的线索。

### R3 · P1 · C3 只裁剪展示字段，仍会由未来内容决定前卷候选

**依据**：`backend/services/final_summary.py:860` 先做全书去重，再依据全书证据数量、跨度和重要度排序、截断（`:867`、`:893`），最后才在 `:935` 按当前卷截止章过滤。去重还使用全书最高重要度/置信度及多数类型，见 `backend/utils/text_utils.py:311`。

**隔离复现**：设中重要度目录上限为 1，前两章分别有线索 A、B，前 10 章候选为 A；只在第 60 章追加 B 的重复出现，前 10 章候选就变为 B。即使删去所有未来证据章号、重算 `last_seen/merged_count`，早期候选已经被全书排序淘汰，无法恢复。

**修订要求**：基于原始出现记录先构建截至 `ch_end` 的视图，再计算可见属性、排序和预算截断；稳定 ID 可共享，但不得用未来统计决定前卷输入。全书目录仅供真正的全书任务使用。

**补充验收**：固定第 1–10 章，任意追加/修改第 11 章之后的内容，第 1–10 章候选集合及提示内容不变。现有 T11 只检查未来章号，覆盖不足。

### R4 · P1 · C2 的原文证据与确认流程没有可执行的数据通路

**依据**：`backend/services/final_summary.py:1610` 的调和输入只有卷摘要和伏笔清单；`extract_key_fields()`（`:330`）提取的是模型生成的摘要/事件，没有原文引用与位置。`backend/api/routes_foreshadow.py:23` 只有分类元数据接口，当前没有回收确认入口。

C2 要求候选引用可以在原文定位，但没有安排原文证据如何进入候选生成流程。只增加输出字段，模型仍可能引用摘要或猜写原句；默认不能升级确认态，又没有明确人工操作入口，会使大量候选长期停留在待确认状态。

**修订要求**：先定义 `source_ref`（书/源版本/章/位置）、证据获取与验证流程。可在既有提取调用中返回定位线索，或确定性检索候选章的原文片段，再按预算选择是否语义复核；不得用摘要冒充原文。若默认采用人工确认，需把确认、驳回、撤销入口及持久化审计纳入 C 的交付范围；若暂不提供，明确产品只交付候选态。

**补充验收**：摘要措辞不在原文、证据位于错误章节、源文本修改、确认后重新总结、撤销确认。引用存在只证明出处存在，不能单独证明语义回收。

### R5 · P1 · C 的新状态语义使全书复检缓存成为必需，D4 不宜整体可选

**依据**：当前全书复检以 `status == active` 选候选（`backend/services/final_summary.py:1384`）；恢复时通过已回收条目不再参与来避免部分重复费用（`:1485`）。

改为 `PROPOSED_RESOLVED` 后，C3 又要求未确认项目与 `OPEN+STALE` 进入复检，原有状态排除方式不再足够。同一输入再次生成总结可能重复调用已经完成的复检；扩大候选集合也可能增加首次运行的调用数。单纯“分批、有预算”不等于满足第 0 节“不增加默认调用”的约束。

**修订要求**：把复检任务完成状态从伏笔是否已回收中独立出来。以来源指纹、候选集合/版本、模型与策略版本标识复检任务，保存成功、无回收、失败、未执行等结果；同输入复用成功结果，失败只补失败项。将这部分从 D4 前移到 C；风格与最终报告缓存仍可选。显式计算新增复检调用，设定默认预算和超额 opt-in。

**补充验收**：相同输入重复运行不新增复检调用；中途停止后只补未完成任务；修改一条相关来源只失效依赖项；无回收的成功结果也可以复用。

### R6 · P1 · A 的 typed verdict 必须贯穿到流水线补跑决策

**依据**：`backend/core/analyzer.py:175` 仅传播错误字符串；`backend/core/pipeline.py:711` 再次以 `classify_message` 判定是否登记 `_fatal_blocks`；补跑过滤依赖该登记（`:255`）。LLM 客户端内也仍有重试阶段边界处重新分类字符串的入口（例如 `backend/core/llm_client.py:1300`）。

A3 明确要求保留结构化判定，但改动清单没有 `analyzer.py`，把 pipeline 写成“仅需时”，容易只修客户端的四个 `_error_action()`。这样内层即停，外层仍可能把未知字符串当作可补跑失败；相反，外层仍可能根据文本误登记永久失败。

**修订要求**：在计划中画定完整传递链：异常/流事件 → 单次调用结果 → 重试结果 → analyzer → pipeline → 补跑/熔断。使用每次调用独立的结果对象或元数据，不借用共享客户端的“最后错误”。外层消费同一个判定，不能重新猜。新大版本可统一内部类型并同步所有消费者。

**补充验收**：结构化账单错误，但显示文本不含可识别错误码；客户端一次停止，流水线也不补跑。并发两个块分别失败/成功，判定不得串用。四条客户端路径测试之外必须有流水线级断言。

## 其他应修订条款

1. **C2 不应无条件要求回收章严格大于埋设章。** 同章先埋后收、同分析块内前章埋后章收都可能成立；应比较有来源位置的顺序。现有提示还禁止“同一批次回收”（`final_summary.py:113`），需要同步删改，否则批大小会影响判定。
2. **基线命令覆盖不完整。** `pytest.ini` 的测试范围为 `backend/tests tests`，计划只写 `python -m pytest backend/tests -q`，会遗漏顶层切章测试。全量命令应为 `python -m pytest -q` 或显式包含两处目录。
3. **E5 被严格执行顺序遗漏。** 把它明确列为必做或 DEFER，并给验收条件。
4. **数据 schema 应前置。** 新版本无需兼容性桥接，B/C 前就应确定章节来源、稳定实体身份、候选/权威状态、策略指纹与缓存键；不要等 E2 才补版本化设计。

## 新大版本可以删减的工作

- 删除无版本知识库读取、旧 rolling 降级、v3 账本迁移、旧 `status` 投影以及迁移前后数量守恒要求。
- B4 可以直接分开 `cooccurrence_edges` 与 `semantic_relationships`，无需先复用 `character_relationships` 过渡。
- E1 可以直接采用有来源与核验状态的 fact records，无需维持 `verified_facts` 字符串兼容视图。
- 新版本从独立数据目录开始；发现不支持的 schema 明确拒绝复用。无需自动迁移，也无需删除原产物。
- 保留 stop/cancel、真实费用统计、原子写、路径边界与本版本断点恢复。这些是运行正确性，并非旧产物兼容负担。

## 建议调整后的执行顺序

1. A：错误判定贯通整个调用与补跑链。
2. 定义新数据契约：章节实际来源、稳定伏笔身份、候选/确认状态、指纹及任务完成记录。
3. B：安全快照、有序 rolling、人物时序、共现与语义关系分离。
4. C：截至当前卷的候选视图、确定性提交、原文证据及确认流程、复检幂等与预算。
5. D/E：其余可靠性、成本治理与质量实验。文件安全、原子写和 CI 可独立前移；基于真实依赖排序，不让它们必须等待全部 C 完成。
6. F：前端消费新契约；其余工程项独立验收。

这些修订完成后，计划可以作为新大版本的实施依据；历史迁移与兼容相关条款不再参与 GO/NO-GO。
