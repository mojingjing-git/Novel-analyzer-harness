## 4. 三个真问题

### P1：上游采集契约有硬伤（**已按外部复核更正表述**）

对同一批 62 条统计：

| 指标 | 结果 | 能不能推出结论 |
| --- | --- | --- |
| `implication` 含推测词（可能/将/未来/后续/恐将） | 38 条 = 61% | **不能**推出"不是伏笔" |
| `clue` 或 `implication` 含疑问要素（谁/是否/究竟/身份） | 5 条 = 8% | **不能**推出"没有可解决的问题" |

**更正**：我先前写"约 92% 不是伏笔"是**没有证据支持的推断**。含未来词无法区分
"原文明确提出的计划"与"模型杜撰"；没有疑问词也不等于没有待交代的事——婚事、承诺、威胁
都可以有可核对的结果。样本里那条 `丁家拟将小姐…许配展昭` 究竟是铺垫还是推演，
必须结合上下文判断，不能靠词表。

**真正的根因在两处**：

- `backend/core/prompt_builder.py:32`（原规则 1）：要求 `implication` **"必须预测具体未来事件"**——
  这是直接指令模型去写剧情预测。
- `backend/core/prompt_builder.py:59`（原 schema）：`"clue": "原文细节"`，必然产出情节摘要。

**已在本次修复**（提交见文末）：
1. 撤掉"必须预测具体未来事件"，改为"说明它暗示了什么**尚待交代**的事；禁止未来式推演"。
2. schema 拆成三问：`clue`（出现了什么）/ `question`（留下什么待交代事项）/
   `answer_criteria`（后文出现什么才算回答）。
3. 规则里补：`question` 必须能被后文回答，氛围/背景/性格描述不算伏笔；
   `answer_criteria` 只写"什么算回答"，**不要写死某个结局**——写死会把"明确取消/反转"
   误判成未回收。
4. `backend/core/anchor.py::mark_leads()`：`question` 与 `answer_criteria` **都为空**才标 `lead`，
   不进复检队列。**刻意不做"疑问词/专名命中"这类词面门槛**（那样会错杀真铺垫、放过假悬念）。
5. 账本 schema v4 → **v5**，携带 `question`/`answer_criteria`/`lead`；旧 v4 账本照常读入。

**已有可复用的便宜线索**：16 章产物里已有 **51 条 `cross_block.unresolved_questions`**，
专项重建时应与 62 条线索一起作为提示，结论仍须由原文支持。

**实施路径（不重跑全部分析）**：
1. ~~定契约~~ → 2. 用现有 16 章原文**只重做伏笔抽取**，生成新账本（旧概括只作提示）
→ 3. 在新候选上修窗口取证与裁决 → 4. 测出质量/调用量/token 后再决定是否扩到整本。
**不需要补齐旧产物字段，也不属于旧账本迁移。**

### P2：复检证据取材错误（已定位，未修）

`backend/services/recheck_v2.py` 当前签名收 `book_text: str`，调用方
`final_summary._collect_book_text()` 把 **blocks 下全部正文**拼起来传进去。
16 章 = 128k 字 ≈ 100k token 打满；整本 64 章 ≈ 400k token，任何模型装不下，
调小 batch 也绕不过（每批仍带全文）。

**候选修法（三档，越往下越贵）**：

| 档 | 做法 | 新增什么 | 代价 |
| --- | --- | --- | --- |
| 最小版 | 本地词面检索定位 → 取 2–3 个原文窗口（每段 800 字）→ 引文必须落在窗口内 | `evidence_index.py`（约 200 行） | 长跨度只能"证据不足"；零词面重叠的回收抓不到 |
| 中档 | 加 `NEED_MORE` 响应，模型可点名"给我第 505 章"再取一轮 | 解析 + 预算 + 循环约 120 行 | 每候选 1–2 次调用；token 约 3 倍于老方案 |
| 完整版 | 再加"摘要当索引"：用已有卷摘要做语义召回，取并集 | 摘要段↔章区间映射 | 多一层易错映射；老账本无锚点仍然无效 |

### P3：能力缺口（新方案对老方案）

| 老方案（摘要）能做、新方案做不到 | 说明 |
| --- | --- |
| **负证据判断**："全书都没交代过" | 摘要覆盖全书，"通篇没出现"本身有信息量；窗口方案只看命中处，命不中就说"证据不足" |
| **老账本 700 条** | 旧数据没有 `anchor_quote`，只能拿描述检索，命中率很低 |
| **需要合并推理的回收**（时间/地点/人物分散在多章） | 摘要可能已合成一句；窗口只给 3–4 段就拼不全 |
| **批量横向比较**（一次 40 条同上下文） | 一条一次调用，失去"第 3 条和第 17 条是同一件事"的判断 |

老方案的实现位置：`backend/services/final_summary.py:1390 _run_global_foreshadow_recheck`，
输入 `full_text = "\n\n".join(volume_summaries)`（`:1476`），批大小 40（`:1426`、`:1477`），
超 15 万字符时 `_plan_recheck_batches`（`:1354`）**按埋设章砍掉"埋设之前的卷"**（`:1361`）——
这条规则本身是对的，值得继承为"检索下界"。

## 8. 环境坑（会让人白跑一天的那种）

1. **代理**：本机 `NO_PROXY` 含 `[::1]`，httpx 会抛 `InvalidURL: Invalid port ':1]'`。
   测试由 `pytest_isolation.sanitize_proxy_env()` 处理；**独立脚本必须自己调**。
2. **模型 hy3（本地网关 `127.0.0.1:3425`）**：强制自适应思考，`thinking.type=disabled` 直接被拒（2013）；
   `max_tokens` 撞上限时**正文为空**——8000/16000 → 0 字，32000 → 206 字，**64000 → 正常**。
3. **MiniMax 额度已打满**（402 `insufficient_balance`），现在该错误判永久错误（不再重试烧钱）。
4. **`AnalysisPipeline` 的落盘位置由 `config.working_directory` 决定**，不是 `directory.parent`；
   不设就落到 repo 根的 `output/`。
5. **全量 pytest 别用管道 `| Select-Object -Last N`**，会挂死；用 `*>` 重定向到文件再 tail。

## 9. 复现 P1 统计的脚本

```bash
python -X utf8 -c "
import json,glob,re
rows=[]
for f in sorted(glob.glob('.tmp_measure_pipeline/**/chapter_*_result.json',recursive=True)):
    rows+=json.loads(open(f,encoding='utf-8').read()).get('foreshadowing',[])
SPEC=re.compile(r'可能|或将|将会|未来|后续|将成|预期|或许|恐将')

print('总数',len(rows))
print('推测语气',sum(1 for x in rows if SPEC.search(x.get('implication',''))))
print('疑问要素',sum(1 for x in rows if Q.search(x.get('implication','')+x.get('clue',''))))
"
```
