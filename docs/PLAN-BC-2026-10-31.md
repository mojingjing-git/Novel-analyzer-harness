# PLAN：B（让 vnext 真能跑）与 C（S9 实测）

A 批（建项目事务化 / 路径校验 / 请求超时）已完成并推送 `c298242`，本计划只覆盖 B 与 C。

## 0. 依赖顺序（不能跳）

```
B0 knowledge 落盘+重建   ← 唯一硬前置：不做则续跑静默降质
   ↓
B1a 单块 async 分析
   ↓
B1b 顺序跑整本（复用 B0 的库、推进覆盖）
   ↓
C1 管道与 token 量级 / C3 锚定重复采样     （C1 依赖 B1a，C3 依赖 B1b）
   ↓
B2 删除项目 / B3 详情页                     （可并行于 C，风险低）
   ↓
C2 标注试点（依赖 C1 的产出）
```

## 1. B0：knowledge 落盘与启动重建（硬前置）

**问题**：`KnowledgeStore` 只在内存；续跑时 `build_prompt_window` 拿到空库，结果与一次跑完
不同，却仍被判"新鲜"。这是**静默降质**——比报错危险。

**做法**
1. `knowledge.py` 增 `KnowledgeStore.from_dict()`（与既有 `to_dict()` 对称；字段版本化
   `KNOWLEDGE_STORE_VERSION=1`）。
2. 落盘位置 `derived/knowledge.json`（`artifacts.write_json_atomic` + `stamp_payload`）。
   写入时机：每块 `publish_result` 成功后**追加**该块记录并整体重写（块数量级几十到千，
   单文件 KB–MB，可接受；不引入增量日志以免两套状态）。
3. 维护 `store_meta`：`source_snapshot_id`、`ordered_result_ids`（按块序）、
   `knowledge_fingerprint`（= `KnowledgeSnapshot.dependency_fingerprint()` 的合集哈希）。
4. **启动重建**：`load_or_rebuild_store(book_dir)` —— 读 `derived/knowledge.json`；
   若 `source_snapshot_id` 与当前 manifest 不符，或 `ordered_result_ids` 与磁盘上
   `SUCCEEDED` 结果序列不符 ⇒ 按块序**重放**（纯本地解析，零 LLM）重建并重写。
5. **依赖闭环**：`ResultRecord` 增 `context_fingerprint`（分析该块时快照的指纹）。
   `classify()` 比对"用当前库重算的指纹"与结果里的记录值，不符 ⇒ `STALE_DEPENDENCY`。
   **这是让"续跑降质"可见的唯一手段**，不做这条 B0 就没有意义。

**验收**：三块结果 + 库落盘 → 删内存重建 → 指纹相同；改第 2 章正文 → 第 3 块
`STALE_DEPENDENCY`；`derived/knowledge.json` 损坏 → 走重放重建且不崩。

## 2. B1a：单块 async 分析

**新文件 `backend/vnext/analyzer.py`**
```
async def analyze_block(book_dir, plan, *, client, limits, strategy, verify_chapter=None) -> BlockRun
def make_chat_caller(client) -> Callable[[str], Awaitable[str]]     # 适配 llm_client.chat
def build_messages(snapshot_window, chapters_text, title) -> list[dict]
def parse_block_output(raw: str) -> dict   # facts/characters，失败抛 UNPARSEABLE_ARTIFACT
```
- `client` 是 `LLMClient`（`async def chat(messages, ...) -> LLMResult`，`llm_client.py:498`），
  **全程 async**；同步的文件 IO 走 `asyncio.to_thread`。
- Prompt 结构：system（输出 schema + `CITATION_INSTRUCTION`）+ user（书名、块内正文、
  知识窗口 `truncated` 提示）。窗口为空时明确写"这是故事开头，无前情"。
- 解析：`json_utils.parse_json_robust`；失败必须**显式报错**，不许返回空 dict 当成功。
- 事实校验：`citations.verify_facts_against_book`，章文本由调用方一次性传入，校验零 IO。
- 落盘：`results.publish_result`（含 `context_fingerprint`、`usage` 来自 `LLMResult`）。
- 预算/账本：`budget.reserve/settle` + `TaskLedger.record(kind="analysis")`，与 recheck 同构。

**验收**：3 章项目跑 1 块（用 fake client）→ `results/` 一个 `SUCCEEDED`；`context_fingerprint`
非空；引文伪造 → `UNVERIFIED` 且不阻断落盘。真实 API 1 次冒烟（预算内）。

## 3. B1b：顺序跑整本

**`backend/vnext/runner.py` 增** `async def run_analysis(book_dir, *, client, limits, ledger, budget, max_blocks=None) -> AnalysisOutcome`
- 按 manifest 块序；跳过 `is_block_fresh` 且已完成块；每块后重建/更新库、落盘、推进 `rolling`
  → `queue.apply_progress`。
- `PENDING_RETRY` ⇒ 停止推进（保留 gap）；`TERMINAL_SKIPPED` ⇒ 越过并标 `part`、`partial=True`。
- 返回 `AnalysisOutcome(committed_blocks, coverage, usage_totals, stop_reason)`。

**验收**：3 块全跑 → `commit_cursor==3`；第 2 块失败 → cursor 停 1、`gaps` 有记录、
`claimed_range` 不假装覆盖 3 块；第 2 块补跑后 → cursor 3 且库与"一次跑完"指纹一致。

## 4. B2：删除项目（顺序死在注释里）

1. `os.replace(book_dir, data_root/.trash-<utc ts>-<book_id>)` —— **先 rename**
   （崩溃在后续步骤时，书已经"看不见"，不会复活）
2. 清队列条目（`_QUEUE_LOCK` 内）
3. 不手写"摘索引"：`refresh_index` 生产零调用，索引由 `scan_projects` 现算
4. API `DELETE /api/vnext/books/{book_id}?confirm=<book_id>`；`confirm` 不匹配 → 422
5. `.trash-*` 被 `scan_projects` 跳过；另给 `scripts/cleanup_trash.py`（默认 dry-run）

## 9. 复审结论（2026-10-31，NEEDS_REVISION → 已并入以下修订）

审查逐条核对，六条断言里 4 属实、1 部分、**1 不属实（实质）**：`ResultRecord` 已有
`dependency_fingerprint`，`classify` 已在比对期望依赖——所以"缺字段"是误判，**真正缺的是
把"库/窗口内容"接进期望值**。五条 P1 全部成立，逐条修订：

| # | 审查指出 | 修订 |
| --- | --- | --- |
| 1 | `extracted` 是自由 dict，没有 `SourceRef` ⇒ 重放得到空库（`knowledge.py:166-170` 丢弃无来源事实） | **`extracted` schema 定死**：`facts: [FactRecord.to_dict()]` + `characters: [CharacterStateRecord.to_dict()]`，两者都带 `SourceRef`（chapter_ordinal + content_hash）。B1a 必须产出这个形状，否则不许落盘 |
| 2 | `derived/knowledge.json` 读改写不在 per-book 锁内 ⇒ 并发丢事实（`concurrency.LockGuard` 只记录不拦） | **库写路径进 `project.commit_manifest` 同一把书锁**：一次临界区完成"读结果 → 追加 → 写库 → publish"，用 `commit_manifest(book_dir, mutate)` 承载 |
| 3 | 快照指纹测不到 Prompt——真正进 Prompt 的是 `prompt_view` **裁剪后**的窗口，`PromptLimits` 与 `dropped` 都不入指纹 | **指纹 `PromptWindow`**：`facts + states + dropped + limits.describe() + PROMPT_VIEW_VERSION`。改限额、窗口变小都必须让下游失效 |
| 4 | `classify` 拿不到"当前库" | `classify(..., context_fingerprints: Mapping[block_sig, str] \| None)`：由调用方（runner）用当前库算出每块期望窗口指纹传入；不传则退化为原行为（只比前序结果与三版本） |
| 5 | `result_id` 不含 `extracted` ⇒ 同条件重跑用同一 ID 覆盖内容，`ordered_result_ids` 不变，不触发重放 | `result_id` 并入 `extracted_fingerprint`；`store_meta.ordered_result_ids` 改存 `(result_id, extracted_fp)` 二元组，任一变化触发重放 |

两条 P2 也并入：**B1b 跳块判据改 `classify(strategy=...).done`**（`is_block_fresh` 只验源不验依赖）；
**§3 验收修正**——`PENDING_RETRY` 只截断 cursor 不记 gap，故断言 `cursor==1 且 missing 含第 2 块`，
"跳过"必须由调用方显式传入 `TERMINAL_SKIPPED` 集合。

另两条：**B2 的队列删除改 remove-if-present**（`dequeue_book` 现无条目抛 `NOT_FOUND`，
rename 后抛就是"删成功却回 404"），并在分析运行中拒绝删除；**C3 的候选来源写明**：
本批 B1a 不产伏笔候选，C3 用**手工构造的 20 个候选**（正文引用来自合成语料），
并在报告里注明"候选非模型产出，只测判定稳定性"。

**§8 四问的回答（采纳审查意见）**：① 每块整体重写可接受，但必须与 publish 同锁，
并在 >2MB 或 >500 块时切追加日志；② facts/characters 的 schema 按上表定死（含 SourceRef），
否则 B0 无意义；③ C3 每候选 **3 次**，90 次调用只能报"翻转计数"，**不给中位数与区间**；
④ 真实书暂不使用（C1 合成语料已够测量级，C2 需单独点名授权）。
