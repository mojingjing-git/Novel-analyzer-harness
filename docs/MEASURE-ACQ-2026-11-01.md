# 采集契约改版与有界证据包：首轮实测（2026-11-01）

## 一、采集契约改版后的效果（16 章，真实模型）

同一批原文（`三侠五义` 前 16 章 / 128,623 字 / 8 并发 / 870 秒），只改 Prompt 契约：

| 指标 | 改前 | 改后 |
| --- | --- | --- |
| 伏笔条数 | 62 | 60 |
| 带 `question` | —（字段不存在） | **60 / 60 = 100%** |
| 带 `answer_criteria` | —（字段不存在） | **60 / 60 = 100%** |
| 标 `lead`（不可核实） | — | **0** |
| 锚点命中 | 60/62 = 96.8% | 58/60 = 96.7% |

**质量变化（抽样对照）**

改前典型条目：

```
clue: 丁母呼展爷为贤侄，二爷溜往小姐绣户
impl: 丁家拟将小姐丁月华许配展昭，未来将成就侠侣姻缘     ← 剧情预测，没有答案
```

改后同章附近条目：

```
clue    : 赵虎酒桌狂言烧水冲白糖（白玉堂），窗外飞石打杯
question: 赵虎后续是否真遇白玉堂并吃亏？
criteria: 后文出现赵虎与白玉堂直接互动的情节
```

另一条：

```
clue    : 柳洪银柜失十封整银，冯氏劝不报官
question: 柳洪丢失的十封银两下落为何，是否白玉堂所取？
criteria: 后文说明银两去向及取走者
```

**结论**：契约改对了方向——条目从"剧情预测"变成了"可被后文关闭的问题"。

**但要诚实的部分**：`lead` 计数为 **0**，说明"两字段都为空才降级"这条兜底在当前模型上**从不触发**。
它不是一个过滤器，只是护栏。也就是说：**采集质量现在完全依赖模型遵守契约**，
程序侧只能检查"有没有填"，不能判断"填得对不对"。

## 二、有界证据包（`backend/core/evidence.py`）首测

同一批 60 条候选，取前 12 条试跑：

| 指标 | 结果 |
| --- | --- |
| 成为候选 | 7 / 12（其余缺锚点或在章内定位不到） |
| 调用次数 | **7 次**（一条一次） |
| 单次耗时 | 约 33 秒 |
| 判定 | 6 条 `INSUFFICIENT`、0 条 `SUPPORTED` |
| 上下文 | **未再出现 token 超限** |

对比改造前：12 次调用全部因 `prompt is too long: 100001 tokens` 失败。

### 为什么 6 条全是"证据不足"

因为语料只有前 16 章——伏笔的回收本来就在后面几十章。这不是判定失灵，
恰恰是它在正确地说"我看到的范围内没有答案"。

要验证"能不能判出回收"，必须用**整本**。

## 三、这轮修掉的三个实现缺陷

1. **定位用窗口而不是整章**：锚点常落在章末，800 字窗口装不下 → 大量候选被判"锚点找不到"。
   改为"定位用整章、展示用窗口"。
2. **Prompt 里仍塞全文**：批处理模板里 `evidence_text=book_text` 漏改，
   证据包算出来了却没送进提示词。改为按证据 ID 取对应窗口。
3. **默认批大小 12**：一个候选一份证据，合并提问会让模型只答第一条（实测 7 条只回 1 条）。
   默认改为 1，一条一次。

## 四、下一步

1. 整本跑（64 章）：分析约 20 分钟 + 复检约 60 次调用，才能得到"能判定多少条"这个数。
2. 若整本仍大面积"证据不足"，先查锚点与检索词质量，**不要先调判定阈值**。
3. `lead` 护栏形同虚设，需要另想办法（例如要求 `question` 与 `clue` 不得同义复述），
   但这属于采集侧的二次打磨，不该和复检混在一起做。
