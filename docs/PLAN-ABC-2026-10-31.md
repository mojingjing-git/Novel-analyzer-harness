# PLAN：A/B/C 三批

## 0. 一句话

A 是"把会误导人的失败修正确"，B 是"让 vnext 能真的跑一次分析"，C 是"用真实数据回答
'要不要改 Prompt 组织方式'与'接口 B 的判定稳不稳'"。

**顺序不能换**：C 依赖 B 的分析流水线（C1 要真实跑 Prompt，C3 要真实裁决链路）。

## 1. A：质量缺口（先做，量小、收益直接）

| # | 问题 | 做法 | 验收 |
| --- | --- | --- | --- |
| A1 | `create_project` 非事务：中途失败留下无 `manifest.json` 的目录，下次被 `registry` 判成 `LEGACY_DIR` | 先写到 `.staging-<uuid>/`，全部写完后 `os.replace` 到最终目录；失败 `rmtree` 暂存目录。**manifest 必须最后写** | 注入"写到一半失败" → `data_root` 下无残留目录、无 `LEGACY_DIR` |
| A2 | `book_id`/`dir_name` 直接拼路径 | 白名单 `^[A-Za-z0-9][A-Za-z0-9_.-]{0,63}$`；拒绝 `.`/`..`/绝对路径/盘符/保留名（`CON`、`NUL`…）；最终 `resolve()` 必须落在 `data_root` 之内 | 用例覆盖 `../x`、`C:\x`、`a/b`、`CON`、超长 |
| A3 | `request()` 无超时/`AbortSignal` | 默认 30s `AbortSignal.timeout`，长任务用 per-call 覆盖；中断映射成 `TIMEOUT` 码 | 前端单测：超时抛 `TIMEOUT`；按钮在超时后恢复可用 |

## 2. B：让 vnext 能跑一次分析

拆三个子批，**每批都能独立验收**，避免一次性大改。

### B1a 单块分析（最小闭环）

- 新增 `backend/vnext/analyzer.py`：`analyze_block(book_dir, plan, *, client, limits, strategy)` →
  用 `prompt_view.build_prompt_window` 组 Prompt → 调 `llm_client.chat` → `parse_recheck` 之外的
  **结构化解析**（复用 `json_utils.parse_json_robust`，但失败要报 `UNPARSEABLE_ARTIFACT`）→
  `results.publish_result` 落盘。
- 真实模型调用方：`make_llm_caller(client)` 适配 `llm_client` 到 `call_model` 契约。
- 验收：合成 3 章项目跑 1 块 → `results/` 有 1 个 `SUCCEEDED` 结果 + `manifest.active_results` 已登记；
  真实 API 各 1 次（预算上限见 §5）。

### B1b 顺序跑整本 + 覆盖视图

- `runner.run_analysis(book_dir, *, client, limits, budget, max_blocks=None)`：按 manifest 块序跑，
  每块推进 `rolling` 覆盖，`PENDING_RETRY` 停下、`TERMINAL_SKIPPED` 越过后标 `PARTIAL`。
- 复用 `budget` 预留/结算与 `TaskLedger` 记账（`kind="analysis"`）。
- 验收：3 块项目全跑完 → `commit_cursor==3`；中间一块失败 → cursor 停在 1、`gaps` 有记录。

### B2 删除项目

- 顺序固定：**摘队列 → 摘索引 → 目录 rename 成 `.trash-<ts>` → rmtree**。
- rename 而非直接删：`.trash-*` 被 `registry` 跳过（点号目录），界面立刻消失且不会被误判成
  `LEGACY_DIR`；rmtree 失败也不影响"它已经不在列表里"。
- API：`DELETE /api/vnext/books/{id}?confirm=<book_id>`，`confirm` 不匹配返回 422。
- 验收：删后 `GET /books` 不含它、队列无悬挂条目、`.trash-*` 残留可被清理脚本扫出。

### B3 界面补齐

- 项目详情页 `VnextDetailPage.vue`（路由 `/vnext/:bookId`）：块列表（`done`/`stale:*`/`missing:*`）、
  "开始分析"（B1b 接上后）、"删除项目"（二次确认输入 `book_id`）。
- 队列区加"重启后校正"按钮（`POST /queue/restore`）。
- 验收：`npm run build` + 便携包冒烟新增两项。

### B4 明确不做（本批）

总结/报告/图谱/地图/风格/聚合/导出这七域**仍然不做**。理由：它们需要 vnext 的知识库落盘、
账本、聚合与导出全链，属 S5–S9 按域重写，不是"界面补几页"。本批只把"能跑一次分析"打通。
**这是本计划最需要复审确认的取舍。**

## 3. C：S9 实验（依赖 B1a）

### C1 Prompt 组织方式（A/B/C）

- 三组：`A_duplicated`（现状：主线 + 逐章）、`B_dedup`（去重历史）、`C_minimal`（只给最近 N 章摘要）。
- 样本：**24 章合成语料**（`backend/tests/fixtures/vnext_corpus.py` 已有）+ 可选真实书 50 章
  （需用户点书名，本计划默认只用合成语料）。
- 每组 3 次重复取中位；指标：prompt tokens、completion tokens、JSON 结构合法率、事实条数。
- 输出 `docs/MEASURE-S9-C1-<date>.md`，**只写事实与区间，不下"选哪个"的结论**——样本量不够时
  明确写"不确定"。

### C2 标注集准确率

- 本批只做**试点**：10 章手工标注（我标注，标注口径与被标注原文一起落盘，便于他人复核）。
- 指标：事实召回（模型产出 vs 标注）/ 误报（无出处的事实数）/ 引用定位成功率。
- 明确边界：10 章只能发现"明显坏"，不能给出置信区间；**全量标注需人工，需另排期**。

### C3 接口 B 锚定风险

- 设计：同一候选，A 组给"按故事顺序"的证据，B 组给"随机顺序"，C 组隐藏候选答案只给正文；
  比较 `SUPPORTED`/`INSUFFICIENT` 的翻转率。翻转率高说明判定依赖呈现顺序，属锚定风险。
- 样本：合成语料 20 个候选 × 3 组 = 60 次调用。

## 4. 预算与安全

- 总调用上限：**≤ 200 次、≤ 2,000,000 prompt tokens**；每段跑前先 dry-run 估字符量。
- 真实 API 用 `config.json` 里已存的配置；脚本内进程级清理代理变量（已知 `NO_PROXY` 缺陷）。
- 任何超限立即停并如实报告"未完成"，不静默降级。
- 全部实验用合成语料，**不把真实作品发出**（除非用户点名允许）。

## 5. 验收（本批完成定义）

1. A1–A3 有用例；A1 的"半成品目录"用例能红→绿。
2. B1a/B1b 能在合成语料上跑完整本，`commit_cursor` 与 `gaps` 正确。
3. B2 删除后四处状态一致（目录、索引、队列、界面列表）。
4. B3 `npm run build` 通过 + 便携包冒烟通过。
5. C1/C3 有真实 usage 数字与 `docs/MEASURE-*` 记录；C2 试点标注集与指标落盘。
6. 全量 `python -m pytest -o addopts= -q` 通过；`docs/VERIFY-LOG.md` 每条写明全量/相关集。

## 6. 需要复审拍板的四件事

## 7. 复审结论（2026-10-31，只读审查，NEEDS_REVISION → 已按修订实施）

审查逐条核对了本计划对现状的断言：A1/A2/A3/B1a/B2 **属实**，**B3 部分不属实**（两个端点早已存在，
`routes_vnext.py:164` / `:173`，前端 `client.ts:394` 也已接——所以 B3 只剩"详情页 + 按钮"）。
以下五条修订已并入本计划：

1. **B1 的 async 契约定死**：`llm_client.chat` 是 `async` 且返回 `LLMResult` 对象（`llm_client.py:498`），
   不是同步 `call_model`。`analyze_block` / `run_analysis` **全部 async**，路由里 `await`；
   同步部分走 `asyncio.to_thread`。**不允许**在 FastAPI 处理函数里 `asyncio.run`。
2. **knowledge 必须先落盘，否则 B1b 不许中途停**：`KnowledgeStore` 现在只在内存里、没有
   `from_dict`，`derived_dir` 无人调用。若续跑，`build_prompt_window` 拿到空库，结果与一次跑完
   不同却仍判"新鲜"——这是静默降质。**先做 `knowledge` 的落盘 + 启动重建，再开 B1b。**
3. **B2 顺序改为 rename → 清队列 → refresh_index**：原顺序（先摘队列/索引再 rename）在 2/3 步之间
   崩溃会让目录还在、下次扫描"复活"此书；而且 `read_index/refresh_index` 生产零调用，手写"摘索引"
   是给无人维护的文件做样子。
4. **C3 去掉"隐藏候选答案"组**：接口 B 的契约要求"原悬念 + 候选答案 + 原文"三者齐备，隐藏候选后
   `SUPPORTED` 无定义。改为**重复采样**（每候选 ≥2 次）分离噪声与锚定，与主计划 §477 一致。
5. **C1 语料改为实测口径**：`vnext_corpus.py` 实为 **23 章 / 6 块**（`block_size=4`），每章 2–3 句，
   **不足以回答"Prompt 组织方式"**；因此 C1 降级为"管道可行性 + token 量级"，并在报告里写明
   "不能据此选方案"。A 组来源也要写明：vnext 目前没有 Prompt 组装器，A 组用 `prompt_view` 的
   现有拼法做基线。

另两条采纳：
- **A1 on Windows**：`os.replace` 目标已存在会 `WinError 5`（不可自愈）、跨卷 `EXDEV`、句柄占用需退避、
  `rmtree` 遇只读文件失败。已按此实现：暂存目录建在 `data_root` 下、`_publish_dir` 重试 6 次、
  `cleanup_stale_staging` 在 `list_books` 入口清理（因为点号目录会被扫描跳过，不主动清就永远看不见）。
  用例只断言异常路径"无残留"，不宣称"进程被杀也无残留"。
- **A3 重接口清单**：`vnext/projects`(300s)、`splitter/preview`(120s)、`prompt/preview`(120s)、
  `aggregate/run`(300s)、excel 导出(300s)；`TIMEOUT`/`ABORTED` 进错误码映射。

**预算修订**：调用上限 200 → **300**（C1 ≤90 / C2 ≤30 / C3 ≤90 / B1 ≤40 / 余量），
按 `attempts` 计数（`llm_client` 内部重试也是真实计费）；token 上限保持 2,000,000
（审查估算按 1.5–3k/call 只用 0.3–0.6M；一本真实书 2605 章约 651 块 × 2–4k ≈ 1.3–2.6M，
故 2M 只够一本真实书，**真实书实验需单独授权**）。
