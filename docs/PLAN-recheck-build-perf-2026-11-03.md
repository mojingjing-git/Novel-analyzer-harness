# PLAN：复检候选构建提速——惰性分批（A）+ 倒排 n-gram 索引（B）

> 背景：`docs/issues.md`「候选构建是 O(候选 × 全书)，且不受调用上限约束」。
> 本计划只动候选构建的**调度**与**检索实现**，不改任何判定语义、不改检索词生成规则。
> C 方案（multiprocessing）评估后弃用，见 §2 D-1。

---

## 1. 实测依据（2026-11-03，本机，《大奉打更人》921 段 / 4,185,982 字）

| 量 | 实测值 |
|---|---|
| 一条候选的检索词（2~4 字片段） | 84~208 个（`_keywords_for` 穷举生成，几乎不跨候选重复） |
| 单次「词 × 段」子串测试 | ≈ 3.4 µs（921 段 `str.find` 共 3.1 ms） |
| 原实现（评分环也逐词扫） | 688 ms/条 → 整本 1669 条 ≈ **19 min** |
| 现实现（词→段集合缓存，2026-11-02 已落） | 402 ms/条 → 整本 ≈ **11 min** |
| **B 实测：2-gram 倒排索引** | 建 22.0 s / 343,419 键 / 266 万 postings / **226 MB**（set 版） |
| B 实测：113 个真实检索词的 df 查询 | 暴力 333 ms → 索引 **12.4 ms（27×）**，**df 不一致 0 词** |
| B 外推整本 | 22 s + 1669 × ~62 ms ≈ **1.7 min**（6.5×） |

时序问题（与耗时同权）：候选**全部**建完才发第一批请求；构建期间单线程、零输出；
`--max-calls` 只限调用数不限构建数——`--max-calls 2` 也要先算满全书，
外部看就是"卡死"（2026-11-02 两次误 kill 的直接原因）。

## 2. 决策

| # | 决策 | 定案 | 依据 |
|---|---|---|---|
| **D-1** | 方案范围 | 只做 A（惰性分批）+ B（倒排索引）；**C（multiprocessing）弃用** | C 收益上限 ~6× 低于 B 的 6.5×，且引入进程池/取消/双平台复杂度 |
| **D-2** | 索引表示 | `array('I')` 有序 postings（段号 4 字节），估算 ~11 MB postings + 键开销，**不用 set（实测 226 MB）** | 桌面端常驻内存优先 |
| **D-3** | 语义契约 | **逐位等价**：filter-then-verify，df 必须与暴力扫完全一致（词只在"其全部 2-gram 都出现的段"里出现，过滤不漏） | 检索结果变 = 证据包变 = 判定变 |
| **D-4** | A 的记账契约 | `candidates_total` = 资格预检总数（有锚点 + open/active + 非 lead）；预算耗尽时**未建的合格候选落 `not_checked`**；`dropped_*` / `locate_records` 在骨架段算完 | 覆盖守恒与 `summary()` 形状不能变 |
| **D-5** | 检索词生成 | `_keywords_for` 一字不动 | 砍词 = 语义漂移，短词是"换了说法"时的唯一线索 |
| **D-6** | 旧缓存去留 | B 落地后删除 `_chapters_with` 的"暴力扫 + frozenset 缓存"，其职责由索引承担（命中集仍按词缓存） | 避免双份内存 |

## 3. 改动

### 段 A：惰性分批构建（`backend/services/recheck_v2.py`）

1. 构建循环拆两段：
   - **骨架段（一次性，全书 ~0.3 s）**：资格预检、`locate_with_mode` 定位、
     `dropped_no_anchor` / `dropped_ids` / `locate_records` / `input_total` / `leads_skipped`
     记账——全部保留在现有循环里的便宜部分；每条候选留下"待建证据"的壳；
   - **证据段（按批惰性）**：`bundle_for` + segments/evidence 组装（现 `:404-435`）
     挪进波次循环，**发请求前只建本波 6 条**；构建是同步 CPU 活，放在
     `asyncio.gather` 之前逐批做，并 `print`/emit 一条 building 进度。
2. 补问轮（`attempt == 1` 的巨型批次）同样按需构建。
3. 预算耗尽（`outcome.calls >= max_calls`）后，未建骨架不再构建，
   收尾时按现有 `not in done` 逻辑落 `not_checked`。
4. `emit` 增加构建进度事件：`{"stage": "build_candidates", "built": i, "total": n}`，
   测量脚本转发为进度行——构建期不再静默。

### 段 B：倒排 n-gram 索引（`backend/core/evidence.py`）

1. 新增 `_GramIndex`（`EvidenceIndex` 私有成员，**首次 `find_mentions` 时惰性构建**，
   小语料如 16 章 fixtures 几乎瞬时）：
   - 构建：逐段扫描，`2-gram → array('I')` 有序段号（append 后保序，天然有序）；
   - 查询：2 字词 → 二分该 gram 的 postings 直接得到命中段（**精确**）；
     3/4 字词 → 词内两个 2-gram 的 postings **归并交集**做过滤器，
     再对交集逐段 `term in text` **精确验证**（4 字词取 `[0:2]`/`[2:4]` 不相交对，
     3 字词只能取重叠对）；
   - len(term) < 2 的防御分支：退回单次全书扫（现调用方不会产生这种词）。
2. `find_mentions` 的 df 与评分环结构不变：`_chapters_with(term)` 改为
   "索引命中集（精确）+ 按词 frozenset 缓存"，权重公式、求和顺序原样保留。
3. 删除旧的暴力扫路径（D-6）。

### 段 C：对照验收与文档

1. **精确性对照**：新增测试——真实语料（`.tmp_stage0_recheck` 的候选词表）逐词
   对照索引 df 与暴力 df，**0 不一致**；fixtures 小语料回归。
2. **记账对照**：`--limit-candidates 200 --max-calls 40` 跑一轮，
   断言守恒、`not_checked` 含未建候选、定位四面计数与改前一致。
3. **耗时**：整本复检重跑一次，验收 ≤ 3 分钟构建 + 调用段不变（~11 min）。
4. 文档：`issues.md` 性能条目改为"当前状态"（已缓解：构建惰性化 + 索引化，
   剩余成本 X）；`baseline-data.md` 更新整本耗时。

## 4. 验收（全部可脚本判定）

| 项 | 标准 | 方式 |
|---|---|---|
| df 等价 | 真实语料逐词对照 **0 不一致** | pytest（新增） |
| 记账等价 | 预算耗尽 → 未建候选在 `not_checked`；守恒成立 | pytest（新增） |

| 门禁 | `pytest` 全绿（基线 1708+新增）、`ruff` 对改动文件 0 告警 | `run_tests.py` |

## 5. 风险与缓解

| # | 风险 | 缓解 |
|---|---|---|
| R-1 | A 重排 400 行闭包巢引入记账回归 | 骨架/证据分离成纯函数；守恒 + not_checked 两个新测试钉住；对照跑 |
| R-2 | B 内存超预期 | `array('I')` 实测定档（§1 是 set 的数）；若仍超 50 MB 再退位图（921-bit 整数/键，~50 MB） |
| R-3 | B 精确性 | 结构性保证（过滤器只删必不含段）+ 逐词对照 0 不一致 + fixtures 回归 |
| R-4 | 高频 gram 交集过大 | 交集取两 postings 中较小侧起手；验证只跑交集；实测 113 词 12.4 ms |
| R-5 | 构建进度事件破坏现有消费方 | 新事件类型独立命名；测量脚本与 `_recheck_progress_message` 都按 stage 分派 |
| R-6 | 惰性构建与补问轮巨型批次叠加（一次建几百条） | 补问轮本就单批，构建量 = 漏答数，无放大 |

## 6. 不做

- 不改 `_keywords_for` 的词数与生成规则（D-5）。
- 不做 multiprocessing（D-1）。
- 不动 `backend/vnext/resolution.py` 的判定语义与 5 状态机。
- 不改前端；不动判定模型与通道配置。

## 7. 待复审确认的开放问题

1. **骨架/证据切分边界**：除 `bundle_for` 外，`resolved_chapters` / `resolved_units`
   的写入（依赖定位结果）留在骨架段是否正确？有没有漏掉的隐性依赖？
2. **索引表示**：`array('I')`（~11 MB postings）vs 位图（~50 MB）vs set（实测 226 MB）——
   结合"交集要频繁做"，哪个是对的？
3. **惰性建索引的时机**：首次 `find_mentions` 时建（本计划默认），还是 `EvidenceIndex.__init__`？
   审计脚本（16 章小语料）与测量脚本（整本）两个场景哪个更受益？
4. **对照口径**：`--limit-candidates 200` 对照是否足以作为行为等价验收，
   还是必须整本对照一轮（成本 ~12 min）？

## 8. 复审修订（AGY，2026-11-03，全部采纳）

| # | 修订 | 原案 → 定案 |
|---|---|---|
| R-1（P1） | 建索引冻结事件循环 | `find_mentions` 首次同步构建 → **`run_recheck_v2` 波次前 `await asyncio.to_thread(index.ensure_indexed)`**（生产里复检与卷摘要/风格共用主循环，22s 同步构建会让全系统无响应） |
| R-2（P1） | 索引表示 | `array('I')` → **921-bit 整数位图**：`array` 无原生交集、34 万对象头 ~27MB 额外；位图交集是单条 C 级 `&`，O(1) 包含判定，~50–90 MB（实现时实测定档） |
| R-3（P2） | 构建事件破坏文案 | `_recheck_progress_message` 不过滤 stage，构建事件会显示"已核对 0 条" → **增加构建阶段文案分支**；测量脚本 `_on_recheck` 同步处理 |
| R-4（P2） | 词长分支漏界 | 2/3/4/`<2` 之外 `len>=5` 未定义 → 统一三分支：`<2` 全书扫兜底、`=2` 直接查位图、`>=3` 首+尾 2-gram 交集过滤后逐段验证（词出现 ⇒ 其全部 2-gram 出现，交集必含真命中，无漏报） |
| R-5（P3） | `_term_chapters` 缓存无界 | 落地 B 后**彻底删除**实例级缓存（检索词几乎不跨候选重复，frozenset 白占 50–80MB）；命中集只在单次 `find_mentions` 调用内局部存在 |
| R-6（P3） | 对照验收盲区 | `--limit-candidates 200`（真实 LLM、12% 样本）→ **Mock LLM 整本 1669 条离线对照**（纯 CPU、零成本）：改前抓 golden，改后重放，断言 `coverage` / `locate_records` / `dropped_*` / verdict 摘要逐字段一致；另加预算耗尽（`max_calls=20`）变体验证"未建候选落 `not_checked`" |
| R-7（P3） | 死代码 | `recheck_v2.py` 的 `global_text`/`chapter_spans` 全书拼接从未被使用（ruff F841 同报）→ 骨架段重构时清理 |
| R-8（P3） | 自适应阈值 | 开放问题 3 的答案：按预计查询量自适应——合格候选 < 64 条不建索引走暴力（小运行免 22s 固定成本），≥ 64 条才 `to_thread` 预构建 |

§7 结论归档：①骨架/证据切分边界正确、无隐性依赖；②表示选位图；③建索引用
`to_thread` 显式预构建而非首次惰性；④对照口径升级为整本 Mock 离线对照。
